TwistedPear · internal engineering reference

Deterministic abuse-simulation architecture

Why every TwistedPear protocol behavior is written once as a pure state machine, run unchanged in production and in a seeded simulator, and used to game out abuse before the platform is ever exposed to its one viral first impression.

Status: software evidence complete; guarded BLE/LoRa calibration remains — see simulation.md · Re-audited: 2026-07-16 · Audience: platform engineers · Scope: architecture and evidence boundaries

Implementation status. The deterministic kernel, transport/adversary models, persisted production grant lifecycle, recording, shrinking, production-backed campaign paths, historical-policy adapters, independent oracle projections, quorum schedules, social/economic models, and formal twins are implemented. Guarded BLE/LoRa calibration remains an external evidence boundary. See the authoritative status record.

Thesis. Write every protocol behavior as a pure, deterministic, sans-IO state machine — step(state, event) → (state', intents) — with no sockets, no clock, and no randomness inside it. Wrap that one compiled core in real IO adapters to get the production host; wrap the identical core in a kernel that supplies virtual time, one seeded PRNG, and an event queue to get the simulator. Because both environments embed the same artifact, an entire multi-node run becomes a single deterministic history reproducible from (seed, config), and the question "was the simulation accurate?" stops being a research question about model fidelity and becomes a build-system property: the thing being simulated is the thing that ships. On top of that core we run adversaries with Dolev-Yao network powers, global-state oracles, and trace shrinking, and we spend most of that budget on the social and economic abuse that actually kills apps at the viral moment — not only the cryptographic attacks that are easier to reason about.

01Why this exists — the one-chance first impression

TwistedPear is a peer-to-peer "everything app": mini-apps run inside one host, reach each other over whatever transport is available — LAN, internet, Bluetooth LE, or LoRa via Reticulum as the connection-of-last-resort — and touch resources only through a broker that mediates explicit, user-visible grants. Apps find each other at runtime by matching a capability vocabulary: a structured envelope plus an English description, indexed by embedding. None of that needs motivating here; you already believe in it. What needs motivating is the simulator.

The strategic fact is asymmetric. A genuinely compelling P2P app can be adopted virally with zero marketing spend — it spreads because people hand it to each other — but that same property means you get exactly one first impression. If the first wave of users, or the first wave of attackers riding that wave, finds a way to exfiltrate a contact list, drain a battery over LoRa, spoof a trusted peer, or turn the discovery broadcast into a harassment vector, the story is written before you can push a fix. There is no staged rollout to a tolerant beta cohort; virality and exposure arrive together.

So abuse has to be gamed out before full development, not patched after. That is a testing problem with an unusually hostile workload — an adaptive adversary rather than a random one — across a heterogeneous, partitionable network, over a capability surface of hundreds of entries. The only known way to make that kind of testing both thorough and reproducible is deterministic simulation testing, the lineage running from FoundationDB through TigerBeetle's VOPR and commercialized by Antithesis. This document specifies how to apply that lineage to abuse-finding, not just fault-tolerance, for TwistedPear.

Framing

Think of the simulator as a wind tunnel you build before the aircraft flies, using the aircraft's own control surfaces as the model. The value is not that the tunnel resembles the sky; it's that the wing in the tunnel is bit-for-bit the wing that will fly.

02The same-code core — one machine, two environments

The central design commitment is that there is exactly one implementation of each protocol behavior, and it is pure. It computes; it does not act. Given its current state and one input event, it returns a new state and a list of intents — declarative descriptions of what should happen next ("send blob X to peer K", "set timer T for 30 s of virtual time", "store blob B"). It never opens a socket, reads a clock, or calls a random number generator. Those are the three classic wells of non-determinism, and keeping all three outside the core is what makes the core reproducible.

An adapter layer turns intents into reality and reality into events. In production, the adapters are real: an intent to send becomes a Reticulum packet; a wall-clock tick becomes a time event; a socket read completing becomes an io-result event. In the simulator, the adapters are virtual: the same send-intent is handed to a network model that decides — from the seeded PRNG and the link's configured latency and loss — when (in virtual time) the corresponding receive event will be enqueued at the destination node, or whether it is dropped entirely. The core cannot tell the difference, because from inside the core there is no difference: it only ever sees events in and emits intents out.

The following diagram shows the shape of this: the pure core in the middle, feeding two environments that share it verbatim.

This is the move that collapses the fidelity question. In the ordinary way of building a simulator, you write the real system and then write a separate model of it, and every bug you find raises the objection "but does the model actually behave like production?" Here there is no separate model of the protocol logic. There is one artifact. The only things the simulator models are the environment — the network, the clock, the disk — and those are exactly the parts you want to be able to distort at will. As the TigerBeetle team puts it, simulation testing exercises a specific implementation, which is precisely what model checking cannot do (see §5 for how we reintroduce model checking deliberately, at a small scale, without giving up this property).

03The step function — IO, time, and RNG as events

It helps to read step as an abstract machine over an event tape. It has a configuration (its state), it consumes one symbol at a time (an event), and each symbol deterministically produces a next configuration and a batch of outputs. The outputs are not actions — they are requests for actions. Whether and when those requests are honored is somebody else's job. That separation is the whole trick: everything that could vary between two runs (a packet arriving late, a timer firing, a random nonce) enters through the event tape, so if you replay the same tape you get the same run, bit for bit.

type Event =
  | { kind: "time";      now: VirtualTime }          // the clock ticked / advanced
  | { kind: "message";   from: PeerId; bytes: Uint8 } // a peer's bytes arrived
  | { kind: "io_result"; ref: IntentId; ok: bool; ... } // a prior intent resolved
  | { kind: "entropy";   bytes: Uint8 }              // RNG delivered as an input

type Intent =
  | { kind: "send";  to: PeerId; bytes: Uint8 }
  | { kind: "timer"; at: VirtualTime; token: TimerId }
  | { kind: "store"; key: BlobId; bytes: Uint8 }
  | { kind: "need_entropy"; nbytes: number }         // ask for randomness; don't take it

// The one and only signature. Pure. Total. No `await`, no `Date.now()`, no `Math.random()`.
function step(state: State, event: Event): { state: State; intents: Intent[] }

Two subtleties are worth stating explicitly, because they are the ones people get wrong. First, randomness is an input, not a capability. The core never pulls entropy; when it needs a nonce it emits a need_entropy intent and later receives an entropy event. In production that event carries OS randomness; in simulation it carries bytes from the single seeded PRNG. Same code path, different source. Second, time is an input, not a reading. The core never asks "what time is it?" — it is told the time by time events, and it schedules future work by emitting timer intents that come back as time events later. A protocol that reads the clock in the middle of a computation is not reproducible; a protocol that receives the clock as an event is.

The payoff of Fig 2 is that the core is trivially testable in isolation — you hand it a list of events and assert on the intents — but the deeper payoff is what happens when you drive it from a kernel instead of from unit tests. That kernel is next.

04The simulator kernel

The kernel is a single-threaded event loop that owns all the non-determinism the core refuses to own. It holds a virtual clock (an integer that only advances when the loop decides), a single seeded PRNG (every random choice in the entire run — packet loss, adversary coin-flips, scheduling ties — draws from this one stream, so one seed determines one history), and a priority queue of events ordered by virtual time. It runs many logical nodes — honest and adversarial alike — inside that one process. Because there is one clock, one PRNG, and one queue, the run is a single totally-ordered history; because that history is a pure function of (seed, config), any run can be replayed exactly by re-supplying its seed and config.

Network models

A transport class is not a comment in the design doc; it is an executable object. Each link in the config declares its class (lan, internet, ble, lora) and the parameters that make that class real: bandwidth ceiling, latency distribution, independent and bursty loss rates, and a partition schedule (windows of virtual time during which the link is severed). The LoRa model is the one that most changes conclusions — kilobits per second, high latency, tight duty-cycle limits — because "connection of last resort" means the attacks worth simulating there are the ones that exploit scarcity (battery drain, channel saturation, denial) rather than throughput. Making the transport executable is what lets a single scenario ask "what does this abuse look like when the only path between victim and attacker is LoRa?" and get a mechanically consistent answer.

Adversary agents

An adversary is an ordinary node — it has a step and it plays the protocol — plus a set of Dolev-Yao network powers granted by its position: it can drop, delay, reorder, duplicate, and inject messages on links it controls. Within that frame we run three kinds:

  • Scripted / historical-replay. Concrete attack sequences drawn from the history of comparable systems (see §7). These are the accuracy floor: if a known-in-the-wild abuse pattern is expressible against TwistedPear, the simulator must catch it, or the simulator is wrong.
  • Search-based fuzzers. Property-based generators in the QuickCheck lineage that explore the space of event orderings and payloads, with shrinking (below) to minimize any failure they find.
  • LLM-driven attackers. A model in the loop proposing high-level abuse strategies ("register a capability whose description is near the victim's, then probe for the grant"), compiled down to concrete node behavior. These extend reach into the social and semantic attacks that hand-written scripts and blind fuzzers both miss — and because they run as ordinary nodes, anything they find is still a deterministic history reproducible without the model.

Oracles and replay

Oracles are global-state assertions the kernel can check because it sees every node at once: "no blob left any node without a live grant covering it", "no two distinct grants share an id", "a revoked grant never authorizes a later access". When an oracle trips, the recorder already holds the full ordered history, and two mechanisms turn that into something debuggable: deterministic rerun (re-supply (seed, config) and watch the identical failure) and trace shrinking (delta-debug the history down to a minimal reproducer — see §7 and Fig 7). Reproducibility here is not a convenience; it is what makes an abuse finding a fixable bug rather than a ghost story.

05The state-machine discipline — three layers

This is the subtle part, and the part most likely to be eroded under schedule pressure, so it gets the most room. The claim is that "protocol behavior is a state machine" is not a metaphor or a documentation convention — it is an implementation and verification discipline with three distinct layers, each with a different job, kept honest by explicit machinery rather than by good intentions.

Layer 1 — explicit state machines as the implementation kernel

The protocol logic is written as an explicit state machine: an enumerated set of states and a transition table keyed by (state, event). This is not a diagram that accompanies the code; it is the code — or rather, it is data the code interprets. The point is adherence by construction, not adherence by checking. There is no gap between "what the protocol is supposed to do" and "what the code does", because the specification of what it does is the artifact that runs. Production and simulator both embed this one artifact, which is what makes §2 true.

Anti-pattern — the thing this layer exists to prevent

The tempting alternative is to author a prose-and-diagram specification as the source of truth, and then have the production code and the simulator each independently approximate it. This is a trap, and it reintroduces exactly the fidelity gap §2 eliminated:

  • Spec drift. Three artifacts (prose, prod, sim) that must agree will not stay in agreement; the prose ages fastest because nothing executes it.
  • Dual maintenance. Every change is now three edits, and the two you forget are the two that diverge.
  • The fidelity gap, reopened. If prod and sim each interpret the prose separately, "does the simulator behave like production?" is once again an open research question — the exact thing the same-core design was meant to settle by construction.

This is also the historical verdict on heavyweight semantic-description schemes — elaborate machine-readable ontologies meant to describe behavior that some other component then implements. They failed for the same structural reason: a description that nothing executes drifts from the thing that does. TwistedPear's own discovery design already leans this way — a big published capability list plus Postel, rather than a heavy semantic scheme — and the state-machine discipline is the same instinct applied to protocol behavior. The rule follows: the machine that runs is the spec. Do not write a second one for humans and hope they converge.

Layer 2 — abstract twins for model checking

Layer 1 buys you an executable that production and simulation share, but executables are bad at answering "is this possible?" over an unbounded space. For the few machines where a subtle ordering or a quorum edge case could be catastrophic — the grant lifecycle, escrow, and the recovery quorum — you also write a small, deliberately abstract twin in a checker: TLA+ for the concurrency and safety/liveness properties, Tamarin or ProVerif for the cryptographic and authentication properties in a Dolev-Yao attacker model. These twins prove things the simulator can only sample: that no interleaving reaches a bad state, over all interleavings, not just the ones a seed happened to explore.

The twin is a second artifact, so it too could drift — and the discipline that prevents that is the arrow in Fig 4 from twin to kernel. The checked model generates conformance traces — sequences of events and expected transitions that are theorems of the abstract model — and the executable machine must accept every one of them. The model does not sit in a drawer being admired; it continuously emits obligations the implementation is mechanically checked against. That is how a proof about a 40-line abstraction stays connected to a 4,000-line implementation. Note the division of labor, which the TigerBeetle team states crisply: model checkers are invaluable for showing an algorithm is correct; they say nothing about whether your code implements that algorithm. Layer 2 does the former, Layer 1 + the simulator do the latter, and the conformance traces are the bridge.

Layer 3 — generated conformance vectors

Because the Layer-1 machine is defined as data — states plus a transition table — it can emit test vectors: for each (state, event) cell, the expected (state', intents). TwistedPear will have at least two implementations of the wire behavior (a TypeScript core and a Python Reticulum core), and the perennial failure mode is that one of them quietly becomes the de-facto spec and the other is judged "wrong" whenever they differ. Generated vectors dissolve that politics: the transition table is the arbiter, both implementations run the same generated suite, and a disagreement is adjudicated against the table rather than against whichever codebase is louder. This is also the strongest defense against the two cores diverging in exactly the byte-level way that §6 is about to warn against.

A concrete machine: the grant lifecycle

All three layers point at the same object, so it is worth seeing one machine drawn out in full. The grant lifecycle is the most security-critical machine in TwistedPear — it is where authority is conferred, exercised, and taken away — so it is a Layer-2 twin, and its transition table drives Layer-1 and Layer-3. 06The Postel boundary — liberal at discovery, byte-strict at grants

Postel's law ("be liberal in what you accept") is good advice in exactly one place in TwistedPear and dangerous advice everywhere else. The design draws a hard line between the two.

At discovery, be liberal. Discovery matches a capability request against a vocabulary of hundreds of entries using an embedding index over structured envelopes plus English descriptions. It is inherently fuzzy, and that is fine, because a wrong answer at discovery is cheap: the worst case of a too-generous shortlist is a probe that fails. If the ranking surfaces a capability that turns out not to fit, the requester tries it, the grant is denied or the handshake doesn't complete, and nothing was lost but a round trip. Liberality here buys resilience to vocabulary skew and phrasing differences at no security cost, because discovery grants no authority — it only proposes candidates.

At the grant boundary, be byte-strict. The grant boundary is where authority is actually conferred — where the broker decides that this app may hold this resource. Here there must be one canonical parser, which is to say one state machine, and it must reject anything that is not exactly well-formed. The reason is the entire family of parser-differential attacks. When two components parse the "same" bytes slightly differently — the classic being HTTP request smuggling, where a front-end and back-end disagree about where one request ends and the next begins — an attacker crafts input that means one thing to the checker and another to the enforcer, and slips authority through the crack. TwistedPear closes that crack structurally: because production and simulator embed the same canonical parser (it is part of the same Layer-1 machine, arbitrated by the Layer-3 vectors of §5), there are not two copies to disagree. A differential attack needs two differing parsers; the discipline guarantees one.

The boundary in one line

Fuzzy where being wrong costs a round trip (discovery); exact where being wrong costs authority (grants). One parser, one state machine, no second interpretation to smuggle between.

The two conformance disciplines pull in the same direction: the byte-strict grant parser is precisely the kind of critical machine that gets a Layer-2 abstract twin, and the Layer-3 vectors are what stop the TypeScript and Python grant parsers from becoming the "two differing implementations" a smuggling attack requires.

07What gets exercised — coverage, completeness, response

A simulator is only as good as the space it searches and the honesty with which it reports what it did not search. Three things structure that: a coverage frame that defines the space, completeness-estimation that calibrates our confidence about the unsearched remainder, and — because the attack set is open-ended — direct simulation of the response rather than only the attack.

The coverage frame

The frame is a product of three axes, and a single simulated scenario is one cell in it:

  • Capability vocabulary — the hundreds of entries an app can request (read-contacts, send-over-lora, hold-escrow, relay-for-peer, …).
  • Attacker position — malicious app, malicious peer, malicious relay, colluding pair, compromised host.
  • Abuse verb — exfiltrate, spoof, deny, drain, correlate.

Enumerating the frame is what turns "test for abuse" into a countable campaign. But a full sweep is astronomically large and, worse, the abuse verbs are not closed — a clever attacker invents a cell you didn't draw. So coverage is necessary but not sufficient, which is why the next two mechanisms exist.

Completeness estimation — calibrated humility

We never claim to have found every abuse. We instead maintain calibrated estimates of what remains, by four means of increasing humility:

  • Formal methods for the kernel. Where a Layer-2 twin exists (§5), the relevant property is proven, not sampled — that region of the space is closed, not estimated.
  • Historical replay as an accuracy floor. The scripted adversaries replay abuses that killed or wounded comparable systems. This does not estimate completeness upward; it sets a floor — any campaign that fails to catch a known-in-the-wild pattern is disqualified before its novel findings are believed. This is the same empirical spirit as Jepsen, which earns its authority by breaking real distributed systems with real fault schedules rather than by arguing from models.
  • Capture-recapture with seeded canaries. Inject a known population of "canary" vulnerabilities and measure what fraction the campaign rediscovers; the miss rate on known bugs is an estimator for the miss rate on unknown ones. Track saturation curves — new distinct findings per thousand scenarios — and treat a flattening curve as weak evidence of diminishing returns, never as proof of exhaustion.
  • Response simulation (its own subsection, below) as the answer to the part that genuinely cannot be enumerated.

Response simulation — because attack is open-ended but resilience is testable

The decisive reframing: you cannot enumerate every attack, but you can measure how well the system contains an attack once it is underway — and containment is a closed, testable property. So the simulator spends real budget on the response, not only the intrusion:

  • Revocation propagation speed — from the instant a grant is revoked, how long (in virtual time, across each transport class including LoRa) until every node that could act on it has stopped?
  • Egress-log attributability — after a simulated exfiltration, can the logs actually pin which app, which grant, which peer? An unattributable leak is a worse outcome than a slow one.
  • Network-kill latency — how fast can the host sever a misbehaving app or peer from all transports, and what is the window of damage before it does?

Measuring these means that even a novel, un-enumerated attack lands in a system whose containment characteristics are known quantities. You may not have simulated that attack, but you have simulated how fast you can revoke, attribute, and cut — and those numbers bound the blast radius of whatever you missed.

Weight the social layer at least as heavily as the cryptographic

A standing bias correction: cryptographic and protocol attacks are more legible — they have clean invariants, they yield to formal twins — so they attract disproportionate attention. But the abuse that historically kills apps at the viral moment is social and economic: spam, harassment, reputation gaming. TwistedPear must model these as first-class adversaries, which means giving the simulator the pieces they need:

  • Spam with cost functions — model the attacker's actual economics (per-message cost over each transport, especially the punishing cost of LoRa airtime) so that "raise the cost of abuse above its payoff" becomes a measurable design goal rather than a slogan.
  • Harassment propagation — model how an abusive interaction spreads across the discovery graph and how quickly containment (block, revoke, sever) arrests it.
  • Reputation gaming — model collusion rings inflating or destroying standing, and test whether the reputation signals discovery relies on survive coordinated manipulation.

Structuring these as adversary agents with cost functions is what lets the social layer share the same deterministic, replayable machinery as the cryptographic layer — and the completeness/response frameworks above apply to a harassment cascade exactly as they apply to a request-smuggling attempt. For naming and organizing the privacy-specific side of this space, the LINDDUN privacy-threat framework and the classic STRIDE threat model are the two checklists worth mapping the abuse verbs against, so that "exfiltrate / spoof / deny / drain / correlate" stays honestly connected to an external taxonomy rather than drifting into whatever the team happened to think of.

Trace shrinking

When any of the above trips an oracle, the raw history can be thousands of events — useless for diagnosis. Delta debugging (Zeller's ddmin) systematically removes events and re-runs; because every run is deterministic, "does this shorter history still reproduce the failure?" is a decidable question, and the algorithm converges on a minimal reproducer. This is the same shrinking idea that Hypothesis and the broader property-based-testing lineage apply to inputs, here applied to whole multi-node histories.

08How to build it, in order

The order matters because the first commandment, if violated once anywhere, silently voids the reproducibility guarantee the rest of the system is built on. One Date.now() buried in a protocol module, one Math.random() for a nonce, and a run stops being a pure function of its seed — and you find out only when a "reproducer" fails to reproduce.

  1. No protocol module ever touches IO, time, or randomness directly. This is the commandment everything else depends on, so it comes first and is enforced, not merely encouraged: a lint/CI rule that fails the build on any import of a clock, socket, or RNG from within the core, plus code review that treats a violation as a release blocker. If you build nothing else this quarter, build the fence and the test that proves the fence holds.
  2. Define the core signature and the transition-table format. Nail step(state, event) → (state', intents) and the shapes of Event and Intent (Fig 2). Represent each machine as data (states + table) from day one so that Layer-3 vectors fall out for free later.
  3. Build the kernel: clock, one seeded PRNG, event queue. Get a single honest node running end-to-end under the kernel and confirm the base property empirically — same (seed, config) yields a byte-identical history — before adding anything else.
  4. Add executable network models. Implement the transport classes (lan / internet / ble / lora) as objects with bandwidth, latency, loss, and partition schedules. Verify that LoRa's scarcity actually shows up in run outcomes; if it doesn't, the model is wrong.
  5. Add oracles and the recorder. Write the global-state invariants (grant coverage, id uniqueness, revocation monotonicity) and the history recorder. Now a violated invariant produces a saved, replayable history.
  6. Add deterministic rerun and trace shrinking. Wire up ddmin over histories (Fig 7). Only now is an oracle failure a minimal, fixable bug report rather than a wall of events.
  7. Add adversaries, weakest-to-strongest. Scripted historical-replay first (the accuracy floor), then search-based fuzzers, then LLM-driven attackers. Each is an ordinary node plus Dolev-Yao powers; add powers only as the position being modeled warrants.
  8. Add the abstract twins for the critical machines. Model grant lifecycle, escrow, and recovery quorum in TLA+/Tamarin/ProVerif, and wire the conformance-trace arrow so the executable core is continuously checked against them (Fig 4).
  9. Generate conformance vectors and run both implementations against them. Make the transition table the arbiter between the TypeScript and Python cores before either has a chance to become the de-facto spec.
  10. Instrument the response. Add revocation-propagation, egress-attributability, and network-kill-latency measurements so containment is a reported number on every campaign — your bound on the blast radius of whatever you didn't enumerate.
  11. Weight the social/economic adversaries. Give the fuzzers and LLM attackers cost functions and the harassment/reputation models, and budget them at least as heavily as the cryptographic cells. This is the layer that decides the viral first impression.

Steps 1–3 are load-bearing; if any of them is shaky, everything above it inherits the shakiness. Steps 7–11 are where the abuse-finding value actually accrues, but they are only trustworthy because 1–6 made every finding reproducible.

09Limitations and honest ceilings

The design is strong precisely because it is narrow about what it guarantees. Overclaiming here would be its own failure mode, so the ceilings are stated plainly.

The physical world can lie in ways the simulator cannot model

The simulator models the network's behavior, not its physics. A real LoRa link has interference, weather, antenna orientation, regulatory duty-cycle enforcement, and hardware quirks that no latency/loss distribution fully captures. A real BLE stack has OS-level pairing behavior outside our core. Where the physical layer can lie — a radio that claims delivery it didn't achieve, a clock that drifts — the simulator's clean event model is an idealization, and some abuses will live in that gap. Historical replay and, ultimately, guarded real-world testing are the only checks on it.

The model-fidelity gap is narrowed, not closed

Section 2 collapses the fidelity question only where the protocol or service logic is literally shared. The grant lifecycle and selected protocol machines meet that bar. The current coverage service and historical targets do not yet do so: they are deterministic test doubles that model expected production effects. Environment models are also genuine approximations. When the simulator says an attack fails, that verdict is only as good as both the shipping-path provenance and the network/adversary model it exercised. The target architecture moves fidelity risk into small adapters and models; the current implementation has not completed that move for every counted path.

The attack set is open-ended

No coverage frame closes over an adaptive adversary's imagination; the abuse verbs are a working taxonomy, not a proof of completeness. This is exactly why §7 leans so hard on response simulation and calibrated humility: we do not pretend to have enumerated every attack, we measure how fast we contain the ones we didn't, and we report saturation and canary-recapture numbers as estimates with error bars rather than as guarantees. The correct posture is a floor we can defend (known abuses caught, critical machines proven, containment measured) under a ceiling we admit (novel social attacks, physical-layer lies, model gaps).

The honest summary

What the current implementation guarantees: a violation in the registered model is reproducible and minimizable; the declared authority relations have checked formal twins; and modeled containment is measured. A finding is a shipping-product finding only when its scenario is backed by the named shipping component. Current campaign and historical test doubles do not yet meet that condition. It also does not guarantee that every attack has been found or that environment models match physics.
